# Unicode 乱码诊断独立审查（2026-09-29，证据修订版）

审查对象：`.agents/runs/unicode-comparisons-20260929.json`（17 个 MCP 用例）、`.agents/runs/unicode-native-comparisons-20260929.json`（18 个原生用例，事件数组均已逐条核对）、`src/runtime/plan.rs`、`src/runtime/execute.rs`、`src/backend/dispatch.rs`、cargo registry 中 enigo-0.3.0 Windows 源码。只读分析，无 GUI 操作。

**重要修订声明：本版取代初版基于"6 个原生短探针全部成功"得出的结论。后续 12 个原生用例（长文本 6 例 + 消融 6 例）已复现与产品完全同形的乱码，初版"原生实验未复现失败/未构成时序排除"的整体判断作废；但根因组件仍未定位，原生证据也不能证明产品侧每次失败都同因。**

## 一、已证实 vs 假设

**已证实（证据可直接支持）：**
- 乱码是**间歇性**的。MCP 批量下 case 03 文本 `Unicode 测试 ✅` 失败 1 次（actual=`Unicode ✅✅✅✅`）；**同一文本**后续经批量模式成功 **6 次**（case 09 + case 13×5）。case 08（`Unicode 测试 Z`）与 case 10（`中文测试甲乙丙`）是**不同文本**，不计入同文本成功统计。
- 同文本、同目标进程下批量失败而逐字符成功（case 03 失败 vs case 04 成功），属"发送方式"差异而非"文本内容"差异。
- 原生 18 例：**11 匹配 / 7 失败**。短文本 6 例全过；长文本 `你好，世界 🌍 | Unicode 测试 ✅ | 本文档共 3 段（含本段）` 下 **batch 2/2 失败、char0 1/2 失败（第 5 例通过）、char10 2/2 失败**；消融组中 noemoji-batch（不含 emoji、不含代理对）同样失败，emoji-short 两种模式通过。
- **同一可观察乱码（`）`重复坍缩等）在脱离 MCP/Runtime/enigo 的纯原生脚本中复现**——这些组件不是产生同类现象的必要条件；原生失败所在的输入处理/目标应用链路尚待细分，不能据此排除产品侧另外存在问题。
- 原生短文本各模式的 SendInput 调用数**不同**：batch 模式 `sendinput_calls_total=2`，char0/char10 模式 `=13`（24 事件拆 13 次调用）；长文本 batch=2、char 模式=39。不能笼统说"都用了 2 次调用"或"各模式产物等同"。

**假设（未证实，不得当结论）：**
- "单批事件过快、目标端处理不过来"——与批量/长文本失败率高一致，但短文本批量成功 6+ 次且原生 char 模式（多次调用）在长文本下也 3/4 失败，因果未建立。
- IME/键盘布局/修饰键残留干扰——失败前后的目标线程键态、IME 状态**均未采集**，纯猜测。
- dwExtraInfo 标记差异导致目标端过滤差异——无证据。

## 二、64 字符分块是否适用于失败用例

**不适用。** `TEXT_CHUNK_CHARS = 64`（`src/runtime/plan.rs:36`）按字符数切分。case 03 为 12 字符；MCP 多行 case 05 从 JSON 计算 `len(expected)` = **34 个 Python 字符**（35 个 UTF-16 单元），原生长文本同理均小于 64，各编译为单个 `PlanEvent::Text`。分块边界类假设可排除。执行器对 Text 事件之间只做取消检查（`src/runtime/execute.rs:114-219`）。

## 三、原生证据的意义（修订）

原生实验**已复现失败**，因此不再只是"未复现"记录。它确立了：产品框架和 emoji/代理对不是产生同类损坏的必要条件，三种发送模式都出现过失败。样本不足以定量判断节奏相关性强弱，也不能说产品路径完全无关。它**没有确立**：具体根因组件、目标端（Notepad/系统/IME）与注入链路的责任划分。样本仍小，短文本在 MCP 路径也有失败，不能称其稳定成功。长文本在本轮较易复现，但长度、内容、执行顺序和状态未充分分离，不能确立长度本身的因果关系。

## 四、enigo 源码事实（修正表述）与未证实诱因

1. **KEYUP 的 wScan 对代理对第二单元错用 `result[0]`**（`win_impl.rs:485-495`）：每个 UTF-16 单元发 down（wScan=该单元），但 up 一律用 `result[0]`。对 BMP 字符（`result` 只有 1 个单元）up 与 down 的 wScan 一致，**无此问题**；仅对增补平面字符（如 🌍）第二个单元的 up 事件携带高位代理。此缺陷真实存在，但 noemoji 用例证明它不是乱码的必要条件。
2. **`\r` 并非被静默丢弃**：`text()` 的 match 臂 `'\r' => {}` 只表示不为它排入特殊虚键，随后 `queue_char` 对**每个**字符无条件执行（`win_impl.rs:270-292`），`\r` 会以 U+000D 的 UNICODE down/up 发出；`\n` 则在 Return 虚键 Click 之外**额外**再发一遍 U+000A down/up，产生冗余换行事件。
3. **整串单批 SendInput 是设计策略，不是独立证实的缺陷**：batch 模式将全部 INPUT 一次注入（短文本 1 次 text 调用、2 次 SendInput 含 select_all；char 模式拆多次）。是否为故障诱因待证，不得当结案依据。

**BMP 失败样本（case 03）诱因：未证实。** `✅`、`测`、`试` 均为单 UTF-16 单元，不涉及事实 1；无换行，不涉及事实 2；事实 3 未证实。现有证据无法在"注入链路丢/重事件"与"目标线程状态干扰"之间区分。**不得将上述源码事实当作成因结案。**

## 五、下一步方向（修订，替换初版钩子方案）

- 初版方案的两个过度声明被纠正：**WH_KEYBOARD_LL 钩子观测到事件不等于证明其送达 Notepad**（钩子在目标处理之前截获，无法区分"送达但未被接受"）；**GUITHREADINFO 不暴露 IME 开关状态**，初版"用 GUITHREADINFO 采 IME 开状态"的说法错误。
- 首选下一步：用**标准 owned WinForms 编辑框**与 Notepad 做同文本对照注入——若仅Notepad失败，可优先调查应用特性/文本服务交互；若两者均失败，可优先调查共享输入链路。两种结果都只是缩小范围，不能单独证明组件责任。
- 状态采样限于**文档化 API 的窄范围采集**：注入前后本进程可见的前台窗口句柄、目标线程 id、`GetKeyboardLayout`、`GetKeyboardState`/`GetAsyncKeyState`（仅修饰键）及文档化的 IME 状态 API（如 `ImmGetOpenStatus`，需目标线程上下文或窗口关联，按可行性评估）。**不做全桌面键盘记录，不向用户应用注入钩子或 DLL。**
- 暂缓：拆批 SendInput 对照实验（待建立稳定复现协议后再做，才有判别力）。

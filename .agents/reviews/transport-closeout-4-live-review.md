1. ingress::apply_direct_cancel currently does `active.matches(id) || gate.cancel_if_registered(id)` then ALWAYS global cancel. Cancelling a QUEUED request B must tombstone B, NOT interrupt unrelated ACTIVE request A. Need classify gate state queued/active and only cancel runtime for the active target. Same duplicate logic in server.handle_notification.
2. `gate.take_dispatch_decision(id)` removes registered id, then server separately calls `active.set(Some(id))`. This is still a lost-cancel window between two different mutexes. Accepted→active transition and cancellation lookup must be atomic under shared request-state lock (or equivalent per-request cancellation token with a race-free handoff). Do not paper over with sleeps or reject-once heuristics.

Every valid request is registered, but only tools/call executes take_dispatch_decision. ping/initialize/tools-list/unknown method/invalidarguments return without removing registration; MAX_TRACKED_REQUEST_IDS256 eventually fills. ingress::stamped_frame ignores gate.register(false), silently loses cancellability of later accepted requests. Completion guard must clean EVERY path; actual tracker capacity refusal must be explicit. Duplicate concurrent IDs must not erase another request's cancellation state.
4. generation stamp should be enforced without trusting arbitrary incoming client metadata. Current reader overwrites __ch_gen for validrequests (so raw client spoof doesn't defeat it); ensure direct unstamped paths never become a public bypass. Prefer typed metadata if simplifying; don't require broad refactor solely for style.
